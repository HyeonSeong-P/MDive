# 파일 선택부터 문서 읽기 · 세션별 구현 계획

상태: **S10 완료 / 기존 카탈로그 기기 회귀 1건 별도 잔여 / 2026-10-31**. 기본 웹·상대 Markdown 링크·실패/권한 복구·세션 내 본문 복귀의 구현·관련 검증·독립 검토·수정을 완료했다. 빌드·단위·영향 회귀와 실제 SAF 검증 결과를 아래에 기록한다. S08+S09의 Coil 캐시·SAF 권한 경계를 유지한다. S11+S12는 다음 별도 요청 범위이며 stash 원본은 보존한다.

## 운영 방법

- 한 세션은 아래 표의 **지시받은 실행 묶음 하나**의 구현·관련 검증·독립 검토·현황 갱신까지 수행하고 멈춘다. 다음 묶음을 자동 시작하지 않는다. 기존 S/H/R ID는 범위·완료 기준·진척을 추적하는 체크리스트로 보존한다. 범위가 예상보다 크면 묶음 안의 미완료 ID와 남은 범위를 기록한다.
- 시작 시 현재 브랜치·로컬 변경·앞 단계 결과를 확인한다. 이 디자인/계획 PR이 병합된 `develop`을 기준으로 작업 브랜치를 만들되, 아직 병합 전이면 사용자가 명시한 브랜치에서만 진행한다. PR 병합을 대신 수행하지 않는다.
- 제품 행동·지원 범위를 바꿀 미정 사항은 해당 단계의 게이트에서 사용자와 정한다. 기술 구현 후보·API 조사는 먼저 진행할 수 있으나 후보를 제품 정책으로 간주하지 않는다.
- 묶음 완료 시 `session-prompts.md`에 다음 실행 묶음의 범위·결정 게이트·검증·중단 조건을 따르는 지시문도 작성하고, 사용자에게 해당 절을 읽도록 요청하는 짧은 시작 프롬프트를 안내한다. 다음 묶음의 미정 정책을 미리 확정하거나 구현을 시작하지 않는다.
- 단계별 결과는 이 문서의 상태 표와 마지막 인계 기록에 갱신한다. 검증하지 않은 흐름은 완료라고 쓰지 않는다. 개발 중 중간 빌드는 첫 버전 전체 지원 완료와 구분한다.
- 커밋·푸시·PR·외부 배포는 해당 세션의 명시적 요청을 따른다. 이 문서의 다음 세션 예시는 구현·검증을 요청하며 Git 게시 권한까지 포함하지 않는다.

## 목표와 원본

첫 흐름은 홈에서 파일 하나를 선택해 문서를 읽는 것이다. 기능 범위는 [제품 방향](../product/overview.md), [홈](../product/home.md), [문서 표시](../product/document-viewing.md), [읽기 도구](../product/reading-tools.md)가 소유한다. 이 계획은 순서·작업 크기·진행 현황을 소유하며 제품 정책을 중복 정의하지 않는다.

시각 조합은 [40개 화면 보드](../design/screens/index.html)와 [DS 사용 대응표](../design/screens/component-usage.md)를 참고한다. 실제 구현은 기존 `designsystem` Compose API를 사용한다. HTML/CSS를 Android 화면으로 복사하거나 버튼·배너·시트의 공통 외형을 화면에서 재작성하지 않는다. [DS 가이드](../product/design-system.md)의 4버튼 타입·S/M/L·라이트/다크 pressed·공통 배너 행동 영역·시트 기준을 따른다. 화면 전용 목차·책갈피 행과 배치는 UI가 소유한다.

현재 코드는 `app`의 제품 홈·읽기 호스트와 공통 MVI 베이스, 공통 `designsystem` 라이브러리 및 별도 `designsystem/catalog` 카탈로그 앱이다. S01에서 DS·lifecycle Compose·Hilt·Navigation 3, S02에서 실제 파일 선택·제목·로더를 연결했다. S02 당시 성공 중간 안내는 S03 이후 실제 본문으로 교체했고 S09까지의 승인 프로필을 표시한다. 원문 로더 개발 테스트 호스트도 유지한다. 필요가 없는 새 모듈·렌더러 프레임워크·저장소 추상화·유즈케이스는 만들지 않는다.

공통 기준은 [아키텍처](../engineering/architecture.md), [MVI](../engineering/mvi.md), [Navigation 3](../engineering/navigation.md)다. 사용자 후속 요청에 따라 `app`·`designsystem`·`:designsystem:catalog` 구조와 `minSdk 24`를 사용한다. 카탈로그 앱은 제품 앱에 의존하지 않고 DS 라이브러리를 참조한다. UI → domain ← data 경계를 지키고 Android URI·파일/권한 구현·특정 라이브러리의 파서 AST가 domain 계약을 침범하지 않도록 해당 기능을 도입할 때 경계를 정한다.

## 실행 묶음 · 2026-10-28 재편

S01–S04 완료 후 **19개 기능 ID를 13개 실행 묶음**으로 재편한 순서를 아래에 보존한다. S10 완료 후 현재 남은 범위는 **13개 기능 ID·8개 실행 묶음**이다. 아래 순서는 기존 번호순보다 우선하며, 기능 채택 범위·미정 정책·ID별 완료 기준은 바꾸지 않는다. 다음 요청 예시는 `S11+S12만 진행해줘`다.

- 묶음의 완료 기준은 포함한 ID의 **합집합**이다. 일부 ID만 통과하면 해당 ID의 상태만 갱신하고 묶음 전체는 완료 처리하지 않는다. 각 ID의 fixture·실패 복구·접근성 검증을 생략하지 않는다.
- 정책 질문은 묶음 안에서 처음 필요한 시점에 확인한다. 묶음 지정이 미정 정책을 자동 승인하거나 후속 묶음 구현을 허용하는 것은 아니다.
- 묶음 내부는 선행 결정 → 구현 → 통합 순서로 진행한다. 독립 조사는 병렬화할 수 있고, 검증·독립 검토·인계는 묶음 단위로 통합한다. 같은 전체 suite를 ID마다 반복하지 않고 변경 영향에 맞는 회귀와 발견 사항 수정 후 필요한 재검증을 수행한다.
- S08+S09에서도 로컬 권한 복구와 웹 실패 재시도는 구분한다. S14+R02는 메타/제목/목차를 먼저 연결하고 확장 참조를 이어 연결한다. 이 묶음이 과도하게 커지면 남은 범위를 기록해 분할한다.
- S16을 마지막 R06과 합쳐도 기능별 혼합 본문·부분 실패·선택→읽기→복귀 검증은 각 묶음에서 유지한다. S15 완료 시 홈·저장 기능에 들어가기 전에 기본 읽기 흐름을 점검한다. 별도 전체 통합 회귀 세션은 마지막에 한 번 수행한다.

게이트는 아직 필요한 결정을 드러내기 위한 목록이다. 보안·권한·문법 정책을 이 계획에서 새로 확정하지 않는다. 기본 파서·코드 강조·수식 엔진은 각 완료 단계의 인계를 따르며 후속 엔진은 해당 단계에서 선택한다.

- S01은 화면 계약·앱 조립의 작은 기반 단계다. 선택기·문서 내용은 테스트/Preview 호스트에서 검증하며 가짜 파일을 실제로 연 것처럼 제품에 표시하지 않는다.
- S02의 원문·리소스 상태 검증은 개발 테스트 호스트에서 수행한다. 최종 Markdown 읽기 흐름은 S03 이후 통합한다. 임시 원문 표시를 새로운 제품 표시 정책으로 확정하지 않는다.
- 아직 구현하지 않은 콘텐츠를 조용히 삭제하거나 파싱 성공으로 처리하지 않는다. G-문서에서 합의한 중간 대체 표현과 지원 프로필을 사용하고, 현재 구현한 범위를 검증 예제에 명시한다.
- 각주는 준비된 target 콜백, 수식/이미지는 준비된 slot만 있던 DS에서 실제 해석·엔진·권한을 연결하는 단계다. DS 예시가 파서 fixture나 엔진 적합성 증거를 대신하지 않는다.

## 단계마다 남길 검증

- 변경된 규칙/상태 전이는 단위 테스트, 중요한 실제 사용자 흐름은 필요한 UI/기기 검증을 수행한다. 빌드만으로 선택기·권한·클립보드·이동·렌더 성공을 주장하지 않는다.
- 코드 변경에 맞는 debug 빌드·단위 테스트를 실행한다. main/release 의존성을 변경하는 S01은 release 빌드도 확인한다. DS 변경 시 생성 검사·카탈로그·관련 회귀를 함께 확인한다.
- 관련 기기 테스트가 가능하면 실행하고, 불가능하면 원인·대체 확인·남은 검증을 기록한다. 현재 API 37 에뮬레이터의 기존 Espresso 3.5.1 호환 오류와 HTML `file://` 렌더 제약은 [디자인 검증 기록](../design/screens/README.md)을 따른다. 이를 영구 구현 금지로 해석하지 않으며, 해당 단계에서 실행 가능한 에뮬레이터/테스트 조합 또는 동등한 직접 확인을 마련한다.
- 최종 브랜치 diff를 `change_reviewer`에게 독립 검토받고 조치한다. 사용자 파일·stash는 임의 삭제하지 않는다.
