# 파일 선택부터 문서 읽기 · 세션별 구현 계획

상태: **계획 갱신 / 제품 구현 미착수 / 2026-10-27**. stash의 기존 5단계 계획과 합의 기록을 복원하고 최신 콘텐츠 범위·DS·시각 초안에 맞춰 분할했다. stash 원본은 보존한다. 이 문서 추가는 제품 Android 화면·파일 로더·파서·렌더 엔진 구현 완료를 뜻하지 않는다.

## 운영 방법

- 한 세션은 **지시받은 ID 하나**의 구현·관련 검증·독립 검토·현황 갱신까지 수행하고 멈춘다. 다음 ID를 자동 시작하지 않는다. 범위가 예상보다 크면 해당 ID를 하위 작업으로 나누고 완료하지 못한 부분을 남긴다.
- 시작 시 현재 브랜치·로컬 변경·앞 단계 결과를 확인한다. 이 디자인/계획 PR이 병합된 `develop`을 기준으로 작업 브랜치를 만들되, 아직 병합 전이면 사용자가 명시한 브랜치에서만 진행한다. PR 병합을 대신 수행하지 않는다.
- 제품 행동·지원 범위를 바꿀 미정 사항은 해당 단계의 게이트에서 사용자와 정한다. 기술 구현 후보·API 조사는 먼저 진행할 수 있으나 후보를 제품 정책으로 간주하지 않는다.
- 단계별 결과는 이 문서의 상태 표와 마지막 인계 기록에 갱신한다. 검증하지 않은 흐름은 완료라고 쓰지 않는다. 개발 중 중간 빌드는 첫 버전 전체 지원 완료와 구분한다.
- 커밋·푸시·PR·외부 배포는 해당 세션의 명시적 요청을 따른다. 이 문서의 다음 세션 예시는 구현·검증을 요청하며 Git 게시 권한까지 포함하지 않는다.

## 목표와 원본

첫 흐름은 홈에서 파일 하나를 선택해 문서를 읽는 것이다. 기능 범위는 [제품 방향](../product/overview.md), [홈](../product/home.md), [문서 표시](../product/document-viewing.md), [읽기 도구](../product/reading-tools.md)가 소유한다. 이 계획은 순서·작업 크기·진행 현황을 소유하며 제품 정책을 중복 정의하지 않는다.

시각 조합은 [40개 화면 보드](../design/screens/index.html)와 [DS 사용 대응표](../design/screens/component-usage.md)를 참고한다. 실제 구현은 기존 `designsystem` Compose API를 사용한다. HTML/CSS를 Android 화면으로 복사하거나 버튼·배너·시트의 공통 외형을 화면에서 재작성하지 않는다. [DS 가이드](../product/design-system.md)의 4버튼 타입·S/M/L·라이트/다크 pressed·공통 배너 행동 영역·시트 기준을 따른다. 화면 전용 목차·책갈피 행과 배치는 UI가 소유한다.

현재 코드는 `app`의 Compose 템플릿과 공통 MVI 베이스, 별도 `designsystem` 및 debug 카탈로그다. DS·lifecycle Compose 의존성은 아직 debug 전용이며 Hilt·Navigation 3는 설정 전이다. 첫 제품 UI 단계에서 필요한 main/release 연결과 DI·내비게이션 의존성을 추가한다. 필요가 없는 새 모듈·렌더러 프레임워크·저장소 추상화·유즈케이스는 만들지 않는다.

공통 기준은 [아키텍처](../engineering/architecture.md), [MVI](../engineering/mvi.md), [Navigation 3](../engineering/navigation.md)다. `app`·`designsystem` 두 모듈과 `minSdk 24`를 유지한다. UI → domain ← data 경계를 지키고 Android URI·파일/권한 구현·특정 라이브러리의 파서 AST가 domain 계약을 침범하지 않도록 해당 기능을 도입할 때 경계를 정한다.

게이트는 아직 필요한 결정을 드러내기 위한 목록이다. 보안·권한·문법 정책을 이 계획에서 새로 확정하지 않는다. 엔진·파서 라이브러리도 아직 선택하지 않았다.

- S01은 화면 계약·앱 조립의 작은 기반 단계다. 선택기·문서 내용은 테스트/Preview 호스트에서 검증하며 가짜 파일을 실제로 연 것처럼 제품에 표시하지 않는다.
- S02의 원문·리소스 상태 검증은 개발 테스트 호스트에서 수행한다. 최종 Markdown 읽기 흐름은 S03 이후 통합한다. 임시 원문 표시를 새로운 제품 표시 정책으로 확정하지 않는다.
- 아직 구현하지 않은 콘텐츠를 조용히 삭제하거나 파싱 성공으로 처리하지 않는다. G-문서에서 합의한 중간 대체 표현과 지원 프로필을 사용하고, 현재 구현한 범위를 검증 예제에 명시한다.
- 각주는 준비된 target 콜백, 수식/이미지는 준비된 slot만 있던 DS에서 실제 해석·엔진·권한을 연결하는 단계다. DS 예시가 파서 fixture나 엔진 적합성 증거를 대신하지 않는다.

## 홈·읽기 도구 후속 단계

기존 stash에서 첫 읽기 흐름 이후로 분리했던 기능이다. 첫 버전 합의 범위를 유지하고 아래 ID별로 한 세션씩 진행한다. 시작 전 해당 기능 명세를 다시 확인하고 커진 작업은 더 분할한다.

| ID | 선행 | 범위·완료 기준 | 상태 |
| --- | --- | --- | --- |
| H01 | S03, S10의 문서 식별/접근 경계 | 즐겨찾기·최근 문서의 식별/기록/정렬/재연결·저장 실패 경계 확정 후 영속 목록·부분 실패·재선택·목록 제거 확인. 원본 비삭제, 앱 재실행 유지, DS 문서 행·복구 배너·확인 다이얼로그 사용 | 미착수 |

## 단계마다 남길 검증

- 변경된 규칙/상태 전이는 단위 테스트, 중요한 실제 사용자 흐름은 필요한 UI/기기 검증을 수행한다. 빌드만으로 선택기·권한·클립보드·이동·렌더 성공을 주장하지 않는다.
- 코드 변경에 맞는 debug 빌드·단위 테스트를 실행한다. main/release 의존성을 변경하는 S01은 release 빌드도 확인한다. DS 변경 시 생성 검사·카탈로그·관련 회귀를 함께 확인한다.
- 관련 기기 테스트가 가능하면 실행하고, 불가능하면 원인·대체 확인·남은 검증을 기록한다. 현재 API 37 에뮬레이터의 기존 Espresso 3.5.1 호환 오류와 HTML `file://` 렌더 제약은 [디자인 검증 기록](../design/screens/README.md)을 따른다. 이를 영구 구현 금지로 해석하지 않으며, 해당 단계에서 실행 가능한 에뮬레이터/테스트 조합 또는 동등한 직접 확인을 마련한다.
- 최종 브랜치 diff를 `change_reviewer`에게 독립 검토받고 조치한다. 사용자 파일·stash는 임의 삭제하지 않는다.
