# 디자인 시스템 공식 사례 조사

조사일: 2026-10-26. 당근·토스의 공식 공개 문서와 저장소를 읽었다. 아래의 MDive 적용은 이 사례를 바탕으로 한 프로젝트 판단이며, 해당 회사의 전체 내부 운영을 확인했다는 뜻은 아니다. 외형·코드·브랜드 자산을 복제하거나 외부 디자인 시스템 패키지를 도입하지 않는다.

## 당근 SEED에서 확인한 점

- **기초 규칙·컴포넌트·패턴 분리:** 색·타입·간격뿐 아니라 상태·모션·포용적 설계도 기반 규칙으로 다룬다. [Foundations](https://seed-design.io/foundations)
- **값과 의미 구분:** Scale과 Semantic으로 토큰을 나누고, 역할 이름으로 디자인 의도를 전달한다. [Design Token](https://seed-design.io/foundations/design-token)
- **정의와 구현 분리:** 저장소는 토큰·컴포넌트 정의와 스타일 레시피, 생성 스타일, 플랫폼별 구현, 문서를 구분한다. [공식 저장소](https://github.com/daangn/seed-design)
- **변형과 상태 분리:** 버튼은 외형·크기·레이아웃 옵션과 loading·disabled를 별도로 노출한다. 터치 누름과 키보드 포커스의 피드백도 공통으로 정의한다. [Action Button](https://seed-design.io/react/components/action-button), [Interaction States](https://seed-design.io/react/components/concepts/interaction-states)

## 토스에서 확인한 점

- **가이드의 읽는 순서:** 위에서 아래로 큰 구조와 변형을 이해한 뒤 상세 상태·접근성으로 이어지게 구성한다. 큰 조합을 먼저 보여주고 필요한 요소를 설명하며, 컴포넌트 특성에 맞게 불필요한 항목은 생략한다. [가이드 설계](https://toss.tech/article/toss-design-system-guide)
- **컴포넌트가 경험을 소유:** 반복되는 사례를 패턴으로 정리하고 세밀한 상호작용과 큰 글자·화면 읽기 대응을 컴포넌트 안에서 해결한다. [컴포넌트 설계 사례](https://toss.tech/article/toss-design-system)
- **실행 가능한 검토 도구:** TDS의 여러 속성을 실제로 확인하는 ShowCaseExample을 개발과 QA에 활용한다. [Example 앱 운영](https://toss.tech/article/22478)

## MDive에 적용

| 영역 | 이번 적용 | 적용하지 않는 것 |
| --- | --- | --- |
| 문서 구조 | 기초 규칙과 컴포넌트 목록 → 개별 상세 | 제품 화면을 첫 결과로 제시 |
| 컴포넌트 상세 | 목적 → 구성 → 변형×상태 → 동작·사용 기준 → 접근성 | 이름 없는 견본만 나열 |
| 원본 | 토큰 값·역할, 아이콘 경로, 컴포넌트 메타데이터를 저장소에 관리 | Markdown·HTML·Kotlin에 지침을 각각 수작업 복제 |
| 구현 | Foundation 입력·접근성 기능 위에 MDive 외형·상태 구현 | Material 기본 외형을 완성 디자인으로 간주 |
| 검토 | 실행 가능한 Compose 카탈로그에서 직접 선택·조작 | 캡처를 사용자 검토의 기본 산출물로 표시 |
| 확장 | 필요한 컴포넌트부터 검토 후 제품 화면에 조합 | 대기업의 모듈·도구·컴포넌트 수를 선행 복제 |

MDive의 현재 규모에서는 공통 JSON·Python 생성기·Android 라이브러리·debug 카탈로그 두 모듈 구성을 유지한다. 간격 척도와 의미별 색상처럼 이미 필요한 구분을 사용하고, 토큰 계층이나 레시피 엔진은 실제 중복과 변경 요구가 생길 때 확장한다. SEED·TDS의 디자인 값이나 제품 정책을 MDive의 승인 값으로 취급하지 않는다.

## 관리와 승인 절차

1. 컴포넌트의 목적·구성·변형·상태·사용·접근성 기준을 공통 카탈로그 원본에 기록한다.
2. 토큰과 아이콘 원본을 사용해 양쪽 카탈로그와 Compose 컴포넌트를 같은 변경에서 맞춘다.
3. 생성물 검사와 필요한 입력·상태·접근성 검증을 수행한다. 미검증 범위는 기록한다.
4. 사용자는 실행 카탈로그에서 검토한다. **초안 → 사용자 승인**을 구분하며, 승인 이후 제품 화면에 적용한다.
5. 변경은 Git으로 추적한다. API·의미가 바뀌면 같은 변경에 기존 사용처와 문서를 갱신한다. 별도 배포 패키지·외부 호스팅·유료 서비스는 현재 도입하지 않는다.

원본 책임과 실행 방법: [디자인 시스템](design-system.md).
