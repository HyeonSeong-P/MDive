# 제품 기획과 화면 설계서

기획은 이 저장소의 Markdown과 HTML로 관리한다. HTML은 브라우저에서 검토하는 와이어프레임을 포함한 화면 설계서이며, 앱 구현 코드가 아니다. 제품 요구사항이 정해지기 전에는 예시 화면을 확정된 기능으로 취급하지 않는다.

## 문서별 책임

| 문서 | 원본으로 관리할 내용 |
| --- | --- |
| [overview.md](overview.md) | 핵심 사용자, 시나리오, MVP 범위, 제품 전체의 열린 질문 |
| 필요한 경우 추가하는 기능별 Markdown | 공통 정책, 비즈니스 규칙, 관찰 가능한 수용 기준 |
| `docs/product/screens/<slug>.html` | 화면 구성, 요소별 동작, 진입·이동 조건, 로딩·빈 상태·실패 등 화면 상태 |

같은 설명 전체를 두 형식에 복제하지 않는다. Markdown에서는 관련 HTML 화면을 링크하고, HTML에서는 관련 정책과 수용 기준의 Markdown 경로를 안내한다. 브라우저가 Markdown을 렌더링한다고 가정하지 않는다. 미리보기에 필요한 짧은 요약을 넣었다면 원본 링크를 함께 표시하고 같은 변경에서 맞춘다. 두 문서가 충돌하면 구현 전에 해당 원본을 기준으로 정리한다.

## 작성 순서와 상태

1. overview에서 대상 사용자와 핵심 시나리오, 포함·제외·보류 범위를 정리한다. 사용자 결정이 필요한 항목은 열린 질문으로 남긴다.
2. 합의된 시나리오에 필요한 화면 설계서를 작성한다. 기능별 Markdown은 overview가 길어져 분리가 필요할 때 추가한다.
3. 화면을 검토하며 공통 정책과 수용 기준을 구체화하고, 구현 전에 관련 미정 사항을 해결한다.
4. 동작 변경 시 Markdown과 HTML의 해당 원본 및 연결 링크를 같은 변경에서 갱신한다. 변경 이력은 Git으로 관리한다.

화면과 주요 결정에는 **초안 / 확정 / 미정**을 명시한다. 초안은 검토할 제안이며, 확정은 사용자와 합의한 내용이다. 미정에는 질문과 결정이 필요한 이유를 적는다. 구현 중·완료 같은 진행 상태는 합의 여부와 구분해 기록한다.

## 화면 설계서 형식

- 파일명은 내용을 나타내는 소문자 kebab-case를 사용한다. 화면이 적으면 하나의 HTML에 여러 화면을 배치해도 된다.
- 화면에는 문서 전체에서 고유하고 유지되는 ID를 부여한다. 예: `S-01`, HTML anchor는 `id="s-01"`. Markdown에서 `screens/<slug>.html#s-01`로 연결하고, 화면 이동 대상도 같은 ID로 연결한다. 삭제한 ID는 다른 화면에 재사용하지 않는다.
- 각 화면에 이름·ID·합의 상태, 와이어프레임, 번호로 대응되는 요소별 동작 설명, 진입·이동 조건을 둔다. 필요한 화면 상태와 열린 질문도 화면 옆에서 확인할 수 있게 한다.
- 미정인 이동이나 동작은 미정이라고 표시한다. 임의의 동작이나 실제처럼 보이는 가짜 링크로 채우지 않는다. 클릭 동작을 시연한다면 설명과 일치하는 최소한의 프로토타입으로 만든다.
- 와이어프레임의 문구와 데이터는 예시 여부를 표시한다. 시각 스타일이나 샘플 데이터가 합의된 앱 요구사항으로 오해되지 않게 한다.

## 로컬 작성과 확인

아래 독립 HTML 규칙은 기존 화면 설계서에 적용한다. 사용자와 합의한 디자인 시스템은 [별도 원본·생성 관리 규칙](design-system.md)을 따르며, 로컬 글꼴과 생성 CSS를 참조하는 카탈로그를 만든다. 디자인의 시각 검증은 Compose 카탈로그에서 진행한다. HTML 브라우저 렌더 미검증과 Compose 검증 결과를 구분해 기록한다.

- HTML은 UTF-8, 한국어 문서 언어, viewport 메타데이터를 포함하고 `file://`로 직접 열 수 있는 독립 문서로 작성한다. 스타일은 인라인 CSS로 두고 시스템 글꼴을 사용한다.
- 외부 CDN, 네트워크 요청, 별도 빌드·패키지 설치를 요구하지 않는다. JavaScript는 상태 전환 등 검토에 실제로 필요한 경우에만 문서 안에 추가하며, 설명은 JavaScript 없이도 읽을 수 있게 한다.
- 좁은 창에서는 화면과 설명이 세로로 이어지도록 하고, 인쇄 시 내용이 잘리거나 숨지 않도록 한다. 상호작용에는 의미 있는 링크·버튼과 키보드 포커스를 제공하고, 상태를 색상만으로 구분하지 않는다.
- 작성 후 파일을 브라우저로 열어 데스크톱·좁은 창의 렌더링, 인쇄 미리보기, 링크·anchor와 필요한 키보드 동작을 확인한다. 코드 검토만으로 렌더 검증을 대신하지 않는다. 브라우저 도구가 없으면 가능한 정적 검사를 수행하고 렌더링 미검증 사실을 결과에 적는다.
- Markdown에서도 상대 경로와 화면 ID가 실제 대상에 연결되는지 확인한다. 문서만 바꾸는 작업에는 Android 빌드가 필수는 아니다.

검토할 HTML 경로를 결과에 안내하면 사용자가 로컬 브라우저에서 열 수 있다. 공개 호스팅이나 배포는 이 절차에 포함하지 않는다.
